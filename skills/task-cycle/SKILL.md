# Task Cycle: Repeating Cycle for Any Task

AGGG2.0 work cycle (primary source: `CYCLE.md`; based on fable-loop
PLAN→EXECUTE→VERIFY→AUDIT + canon rules). Every task = one loop.
Phases repeat EVERY time, "I remember from last time" doesn't count.

## Workflow (9 Phases — In This Order)

0. **Re-contextualization — request summary.** What do they want, in one or two phrases (task + goal). Summary doesn't match the request text → clarify BEFORE acting, don't execute blind.
1. **Database when the question is about existing project knowledge.** "We covered this before / what did we conclude" → use the verified target project's `findings.py search` and `search.py`; session memory is NOT a source. If the target database/tools are absent or stale, report that and use the documented fallback instead of inventing a database.
2. **Web research for external/current unknowns.** Use the currently verified web tool surface and its required schema; `web-research-camoufox` is the workflow, not proof that a Camoufox MCP server is live. For purely local/exact-context tasks, local files and tests may be the correct first evidence. Research before decisions, not as a ritual for every trivial fact.
3. **Plan — for non-trivial tasks.** Readiness criteria (how we'll verify), what we do, what we consciously DON'T do, risks. Small stuff — skip the plan.
4. **Action.** First, project indexing (no database → `build.py`, freshness → `search.py --refresh`), search and understand code THROUGH the database (`db-first-search`), depth via agent-lsp (`lsp-code-depth`), review via code-review-graph (`code-graph-review`). First look at what already exists (scripts/, db-tools/, database) — don't reinvent the wheel.
5. **Verification — mandatory.** Linter + semgrep + tests (analog of ruff for the language) + CI + live where possible. Site accessibility — through Camoufox, not curl. "It compiled" ≠ "it works."
6. **Findings — into research.db.** After any research/experiment/analysis: `findings.py add` (what we chose, why, what we rejected, links). Otherwise knowledge is lost after the conversation.
7. **Documentation.** Code changed → CHANGELOG. Error repeated → rule in the canon. Experience → skill.
8. **Report.** Brief, result first, honest caveats. If asked to
   explain — like to a dinosaur: audience → layers → analogy → verify
   understanding; visually — structural (tables, lists, highlighting), not
   a wall. Patterns — the archived `aggg2-persona` (sections "How to Explain,"
   "Visual Presentation").

## Gates (Transitions Between Phases)

- **Trivially** — phases 3-7 in compressed form: did it → verified with one check → reported in two sentences.
- **Don't know / not sure** — go back to phase 2 (research), don't guess.
- **Error repeats twice** — change method, get a NEW fact (log, dump, isolation, history), not another blind edit.
- **Irreversible / external / paid** — explicit user confirmation.
- **Stuck for more than 3 fix-verify cycles** — stop, analyze the method (postmortem), rule from the analysis → into the canon.


## Surrounding Loops

- **Install/update:** `setup.py` (idempotent) → verify `run_tests.sh --mirrors` (details in `workspace-setup`).
- **Review:** diff → CRG (impact) → agent-lsp (depth) → check dead-code false positives → tests.
- **Errors:** gotcha → cause → rule in canon → next task starts with that rule. The canon grows only this way — from real cases.

## Checklist Before "Done"

- [ ] Summary matches the request text
- [ ] Existing project knowledge checked when relevant; target root and database availability verified
- [ ] Research done BEFORE code (for non-trivial tasks)
- [ ] Readiness criteria were/are clear
- [ ] Verification: linter + tests + live
- [ ] Findings recorded (findings.py add)
- [ ] Report: result first
