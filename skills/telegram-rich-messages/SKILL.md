# Telegram Rich Messages (Bot API 10.x)

Rich Messages are structured messages built from BLOCKS (not parse_mode
markup). One message can contain text, collapsible sections, tables,
checklists, code blocks, media, and (since 10.3) buttons. Sent via the
`sendRichMessage` method.

## Method

```
POST https://api.telegram.org/bot<TOKEN>/sendRichMessage
{
  "chat_id": <id>,
  "message_thread_id": <topic_id>,          // optional, for forum topics
  "rich_message": { "blocks": [ ...blocks ] }
}
```

Requires a Bot API 10.3+ server. If the token's server predates 10.x you
get `Method not found` — fall back to classic `sendMessage` with
`parse_mode: "HTML"` and `<blockquote expandable>…</blockquote>`.

## ⚠️ LIVE-VERIFIED SHAPES (docs diverge — trust these)

Field-name traps found by probing the real API. The official changelog
names classes (e.g. `InputRichBlockExpandableBlockQuotation`) but does NOT
show the JSON wire format; several intuitive shapes FAIL.

### Blocks — supported `type` values (verified OK)

| type | fields | notes |
|---|---|---|
| `paragraph` | `text`: RichText | base text block |
| `expandable_blockquote` | `text`: RichText, `credit`?: RichText | **collapsible** quote, collapsed by default; field is `text` (RichText), NOT `children`/`blocks` |
| `blockquote` | `blocks`: Block[], `credit`?: RichText | regular quote; field is `blocks` (array of blocks), NOT `text` — `text` → `RICH_MESSAGE_EMPTY` |
| `details` | `summary`: RichText, `blocks`: Block[], `is_open`?: true | collapsible section (like `<details>`); content in `blocks` |
| `pre` | `text`: str, `language`?: str | code block. Type is `pre`, NOT `preformatted`/`code_block` |
| `list` | `items`: ListItem[] | see ListItem below; items are objects, NOT strings |
| `table` | `cells`: Cell[][] | 2D array of cells, NO row wrapper object |
| `divider` | — | horizontal rule |
| `footer` | `text`: RichText | small bottom line |

### Unsupported via sendRichMessage (probed, rejected)

`section_heading`, `heading*`, `preformatted`, `pull_quotation`,
`block_quotation` (use `blockquote`), `quotation`. Headings inside blocks:
use `paragraph` with a `bold` run — the client renders message headings
only from user-entered text.

### RichText — the `text` payload

`RichText` = plain **string** OR **array** mixing:
- plain strings,
- run objects: `{"type": "bold"|"italic"|"underline"|"strikethrough"|"marked"|"code"|"spoiler", "text": RichText}`,
- `{"type": "url", "url": "https://…", "text": RichText?}` — link (text label optional),
- `{"type": "date_time", "unix_time": 1788450000}` — date widget (field is `unix_time`, NOT `date_time`).

Gotcha: `{"type": "text", "text": "…"}` as a RUN is INVALID ("Unsupported
rich text type"). Plain text inside arrays must be a raw JSON string.

### ListItem (inside `list.items`)

```json
{
  "blocks": [ {"type": "paragraph", "text": "item text"} ],
  "has_checkbox": true,     // optional; omit for plain bullet
  "is_checked": true,       // only if has_checkbox
  "type": "1",              // optional ordered marker: "1"|"a"|"A"|"i"|"I"
  "value": 1                // optional number for ordered lists
}
```

Item content lives in `blocks` — a `text` field on the item fails with
"invalid list item type specified".

### TableCell (inside `table.cells[[][]]`)

```json
{"text": RichText?, "is_header": true?, "colspan": 2?, "rowspan": 2?,
 "align": "left"|"center"|"right", "valign": "top"|"middle"|"bottom"}
```

`align`/`valign` are required (defaults untested — set them explicitly).
Rows are plain arrays of cells: `cells: [[cell, cell], [cell, cell]]`.

## Minimal working examples

### Changelog with collapsible sections (the common case)

```python
import json, os, urllib.request
TOKEN = os.environ["TELEGRAM_BOT_TOKEN"]

def send(blocks, chat_id, thread_id=None):
    p = {"chat_id": chat_id, "rich_message": {"blocks": blocks}}
    if thread_id: p["message_thread_id"] = thread_id
    req = urllib.request.Request(
        f"https://api.telegram.org/bot{TOKEN}/sendRichMessage",
        data=json.dumps(p).encode(), headers={"Content-Type": "application/json"})
    return json.loads(urllib.request.urlopen(req, timeout=30).read())

blocks = [
    {"type": "paragraph", "text": [{"type": "bold", "text": "🚀 Release 1.2.3"}]},
    {"type": "paragraph", "text": "Summary line."},
    {"type": "expandable_blockquote", "text": [
        {"type": "bold", "text": "✨ Features\n"},
        "• feature one\n• feature two"]},
    {"type": "expandable_blockquote", "text": [
        {"type": "bold", "text": "🛠 Fixes\n"},
        "• fix one"]},
]
print(send(blocks, chat_id=5094569795))
```

### RichText builder helpers (recommended)

```python
def bold(t):   return {"type": "bold", "text": t}
def ital(t):   return {"type": "italic", "text": t}
def code(t):   return {"type": "code", "text": t}
def spoil(t):  return {"type": "spoiler", "text": t}
def link(url, label=None):
    d = {"type": "url", "url": url}
    if label: d["text"] = label
    return d

def para(text): return {"type": "paragraph", "text": text}
def expq(text): return {"type": "expandable_blockquote", "text": text}   # collapsible
def quote(blocks): return {"type": "blockquote", "blocks": blocks}
def details(summary, blocks, open_=False):
    d = {"type": "details", "summary": summary, "blocks": blocks}
    if open_: d["is_open"] = True
    return d
```

## Editing & fallbacks

- Edit later: `editMessageText` accepts `rich_message` parameter (10.1+).
- Stream drafts: `sendRichMessageDraft` (typing-like streaming of blocks).
- Buttons in-message: `RichBlockButtons` / `RichTextButton` (10.3) — NOT yet
  probed; expect the same JSON-shape trial-and-error, probe first.
- Media inside message: `InputRichBlockPhoto` etc. (10.2 `blocks` variants) —
  not probed here; same advice.
- If `sendRichMessage` → `Method not found` or "unsupported": fall back to
  `sendMessage` with `parse_mode: "HTML"`; `<blockquote expandable>` gives
  the collapsible effect (no tables/checklists though).

## Troubleshooting (live-mapped error → cause)

| API error | cause |
|---|---|
| `type "X" is unsupported` | block type not in the supported table (e.g. `preformatted`, `pull_quotation`, `section_heading`) |
| `Unsupported rich text type` | a run object with unknown `type` — usually `{"type":"text",...}` inside a RichText array; use a plain string |
| `RICH_MESSAGE_EMPTY` | block content in wrong field: `blockquote` needs `blocks`, not `text`; `details` needs non-empty `blocks` |
| `RICH_MESSAGE_CONTENT_REQUIRED` | block content in wrong field: `expandable_blockquote` needs `text`, not `blocks`/`children` |
| `invalid list item type specified` | list item objects missing `blocks` or using `text` instead |
| `Can't find field "cells"` | table rows wrapped in objects; `cells` must be a 2D array of cell objects directly |
| `Can't find field "unix_time"` | date run uses `unix_time`, not `date_time`/`timestamp` |
| `Can't parse InputRichBlockListItem: Object expected` | list items as plain strings; must be objects |
| `Method not found` | server/token predates Bot API 10.x — use HTML fallback |
| `Bad Request: message thread not found` | sending to the GENERAL topic with an explicit id: General (even renamed, root id 1) REJECTS `message_thread_id: 1` — omit `message_thread_id` entirely and the message lands in General. For every other topic `message_thread_id` = ROOT MESSAGE id; userbot `list_topics` returns exactly those ids (verified 2026-09-03: Общение=1, Флудилка=6032, JailBrake=5552…) |
| post lands in the WRONG topic (e.g. changelog twice in «Флудилка») | wrong id→topic MAPPING on the sender side, not API misrouting — the API routes exactly to the id given (2026-09-03: 6032 was assumed «Общение» from conversation context, actually «Флудилка» → duplicate posts). Resolve the topic id via `list_topics` (or the first number in `t.me/<group>/<root>/<msg>` of a message inside the TARGET topic) immediately before sending, and verify actual placement afterwards |
| `deleteMessage` returns ok but message survives | Bot API may report success in forum topics without deleting (2026-09-03: `ok: true` on msg 9396, message stayed). Verify via `forwardMessage`/`getMessages` (both honestly say "not found" vs "found") or userbot `get_message_context`; reliable removal = admin delete from a user account |
| `can't parse InputRichBlock: …` | generic: re-check field names against the tables above |

## Reading Rich Messages back

Bot API `getUpdates` delivers `rich_message` only while unconfirmed; most
MCP wrappers show `[unsupported message type]`. To read rich messages from
history, use MTProto (Telethon): the message object has `.rich_message`
with `.blocks` of `PageBlock*` nodes (`PageBlockParagraph`, `PageBlockList`,
`PageBlockPreformatted`, `PageBlockDetails`, …) and `TextPlain`/`TextConcat`
runs. Workspace session: `~/.openclaw/telegram-mcp/telegram-mcp/.env`
(`TELEGRAM_SESSION_STRING`) — see `_mira_rendered.md` for a worked example
of rendering those blocks to markdown.
