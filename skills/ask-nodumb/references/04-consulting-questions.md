# Consultant's questions: how to move a decision in each situation

## The principle of questions

A question is a tool for moving a decision, not a way to offload work
onto the other person. Don't flood them: one or two questions from the
right level change the conversation more than a dozen listed ones. If a
safe assumption can be made — state it out loud and move on. Paralysis
from questions is worse than an approximate answer with an explicit
caveat.

## Situation: a ready solution was brought in

Someone has it all figured out and asks you to draw it. Don't draw —
first check where the task came from. Questions:

- What was the person doing right before they needed this thing?
- How do they cope now, and why isn't it enough?
- What disappears if nothing is done?
- Are we treating the cause or the symptom?

The most important question is "what disappears". An answer of
"nothing" means the problem being solved is interest, not pain. That's
fine, but then say honestly "we're doing this for interest" — don't pass
it off as user pain.

## Situation: an argument over options

Two or three options, people split into camps. Move the argument from
"which is prettier" to "which is right":

- What does each option optimize, and what does it sacrifice?
- Which option continues the product's image and direction better?
- What is hardest to undo if we're wrong?
- What cheap experiment would separate the options?

The last question often settles everything: instead of endlessly
debating two mockups — a week-long test with real users and one question,
"what would you do with this".

## Situation: it needs simplifying

A request to "simplify" almost always means "this feels too complex to
me". Clarify for whom:

- Who found it hard: a newcomer, an expert, the team?
- Which work demands unnecessary effort?
- What can be revealed later, and what removed entirely?
- Does the simplification strip understanding and control?

The classic mistake is simplifying for the newcomer at the expert's
expense. The expert loses control and leaves. Conversely, "simplifying"
for everyone often hides important capabilities from the newcomer who
doesn't know to look for them.

## Situation: the design is incoherent

Screens don't add up to one product; decisions contradict each other.
Look for the model:

- What image or principle would explain the contested decisions?
- Which elements of one entity behave differently?
- Where is the model not written down and replaced by taste?
- What common rule can be formulated without excess machinery?

Start with contradictions: the same entity behaving differently on
different screens means the model is undescribed and everyone drew from
their own head. Formulate one rule that covers most cases; don't build a
system for its own sake.

## Situation: choosing a visual system

A colour model, tokens, typography need choosing. Questions:

- Which relationship between elements is read first?
- What must the language survive: a theme, states, platforms?
- From which repetitions does a shared token follow?
- Which detail carries meaning, and which is only effect?

The system is chosen for future change: if a dark theme is coming,
colours are built around relationships, not absolute values. Separate
details that carry meaning from decor that merely pleases the eye.

## Typical mistakes

Six mistakes every consultant repeats:

- **Form instead of problem.** Drawing a screen without checking the
  task exists.
- **Early frame.** The tool is chosen before the context is understood,
  and it narrows thinking.
- **False simplicity.** Removal creates work and anxiety, not ease.
- **Aesthetics without a model.** Pretty, but decisions are random and
  unreproducible.
- **Model without an image.** The system exists, but character and
  position don't.
- **Metric instead of judgement.** A number replaces the answer to "is
  this right".

Each mistake is cured by stepping up a level: from form to problem, from
tool to context, from metric to judgement.
