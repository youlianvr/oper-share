# 2026-07-25: inject-patch.js v4 — orphan-class bug

**TL;DR.** Replacing orchestrator.js via `inject-patch.js` broke Bun v1.3.14 with `SyntaxError: Unexpected token ')'`. Root cause — partial regex match on nested `{}` code left an orphan `); }` block on disk.

---

## Symptom

Freebuff Desktop won't start:

```
[2026-07-25T12:37:48.271Z] Starting Freebuff orchestrator
SyntaxError: Unexpected token ')'
Bun v1.3.14 (Windows x64)
```

`node --check` reports OK (V8 lenient). **Only `bun --check` catches this error** — Bun is stricter about byte-offset in 127k-line files.

## Root Cause

`inject-patch.js v4` used regex character-class replace (`[^}]*`) for cleanup of old injection before inserting new. This pattern:

1. Matched multi-line code `try { … } catch(e) { … }`, but `[^}]*` stops at the first `}`.
2. Inside the `try { require(...) }` body there's an object literal — another `{}` pair. Regex only eats up to its close.
3. The outer `}` (closing the `if` wrapper) stays outside the match.
4. The old "remaining" fragment stays after the new block — extra `); }`.

Specific discovery location: `orchestrator.js:123807` (right after `discoverUnknownPrs();`), line starts with `);`. This is the extra `;` from the old `tel { … } catch(e) { … }` v3 block that v4 only partially replaced.

## Actual Structure of Broken orchestrator.js

```js
// line 123805 — was
this.discoverUnknownPrs();
// line 123806 — new v4 injection (intact)
if (!globalThis.__fbProxyInstance) { try { … } catch(e) { … } }
// line 123807 — orphan from old v3 (extra)
); } catch(e) { console.error('[fb-proxy] injection error:', e); } }
```

Bun parser: after the first line expects either end of statement or new construct. Extra `); }` breaks the parser.

## Fix: inject-patch.js v5+

Fully rewritten. Key principles:

### 1. Marker-wrapping (Instead of Regex on Code)

```js
/* __FB_PROXY_INJECTION_BEGIN__ */
if (!globalThis.__fbProxyInstance) { … }
/* __FB_PROXY_INJECTION_END__ */
```

Cleanup phase uses line-by-line findIndex to locate `MARK_BEGIN`, then `MARK_END`, splices the content. **No regex character-classes on multi-line code with `{}` inside.**

### 2. Line-based Edits

```js
const lines = fileContent.split(/\r?\n/);
// … splice operations …
const newContent = lines.join(eol);
```

Parsing by real newlines — no regex-matches for code. Indent copied from target line (`this.discoverUnknownPrs();`).

### 3. JSON.stringify for require Path

```js
const PROXY_REQUIRE_LITERAL = JSON.stringify(PROXY_PATH);
```

Safe for all special characters — backslashes, quotes, control chars.

### 4. Structural Balance (Not Runtime Check)

Each injection line is built so `(` count = `)` count and `{` count = `}` count by construction. For example:

```js
'if (!globalThis.__fbProxyInstance) { ' +
  'try { globalThis.__fbProxyInstance = require(' + JSON.stringify(PROXY_PATH) + ')' +
  '(this, { promptAiSdkStream: globalThis.__fb_promptAiSdkStream || null }); ' +
  '} catch (e) {} ' +
  '}'
```

Manual count: 4 opens `(` + 4 closes `)`, 4 opens `{` + 4 closes `}`. Balanced.

### 5. Atomic Write via tmp + rename

```js
const tmpPath = ORCH_FILE + '.tmp';
fs.writeFileSync(tmpPath, newText, 'utf8');
fs.renameSync(tmpPath, ORCH_FILE);
```

On rename failure — `.tmp` stays with WARN. **No auto-delete** (H2 trash-only rule).

### 6. Idempotent Cleanup Phase

Each re-run of the injector:
- Finds markers → line-by-line by index splices the block → re-introduces fresh block.
- Doesn't find markers → just injects (first run after clean restore from `.bak`).
- Doesn't find `discoverUnknownPrs()` → `process.exit(1)` with ERROR, file not written.

## Rule (Anti-pattern)

> **Never apply a regex replace (`s/…/…/`, `String.replace()`, `sed -i`) to multi-line code containing nested `{}` / `[]` / `()`.**
>
> Use line-based edits (`split` / `splice` / `join` or `awk` / `python fileinput` line-by-line) and idempotent namespace markers instead.

The same principle applies to:
- Codemodding over `.tsx`/`.vue` SFC
- AST transformations over `.min.js` bundles
- Any single-step regex replace across lines longer than `~80` chars

## Bun vs V8 vs Node — Parser Strictness

`new vm.Script(text)` (V8 Script-context) is **stricter** on `import`/`export` than `node --check` (same V8, but in CJS-module-context).
Bun is **stricter** on byte-offset errors in very large files (127k lines).
V8 Script-context **rejects `import.meta`** (Module-only construct).

This means: for syntax checking a large file generated by Bun runtime, **use the same engine** (`bun build --target=bun --no-bundle`). V8 validators can miss class of bugs.

For Freebuff environment — the orchestrator.js parser itself is Bun v1.3.14. Pre-write check via `new vm.Script` caught false positives for `import.meta`. That's why v5.2 removed parse-check entirely and relies on structural correctness by construction.

```

```

## Side Effects I Didn't Expect

- **Bun parser is sensitive to CRLF in large files** — we saw mixed line endings nearly broke the parser.
- **Source files with CRLF** vs dist mirror with LF → git diff shows phantom byte-changes after checkout. Locally `.gitattributes` with `*.py text eol=lf` solves this on our repo, but in Freebuff Desktop install dir each effect must be updated together.

## Recovery: Re-create `.env` with Correct Token

If bot is silent (no python.exe with fb-telegram-bot.py in `Get-Process`):

```bash
# Re-create .env alongside Freebuff.exe
cat > /c/Users/pc/AppData/Local/Programs/@codebufffreebuff-desktop/.env <<EOF
# Freebuff-specific Telegram bot token (@BotFather).
# Don't confuse with main TELEGRAM_BOT_TOKEN — that's for other bots.
FB_TG_BOT_TOKEN=<your token>
EOF

# Restart Freebuff Desktop via shortcut — DON'T kill manually (we live inside the process)
```

After manual restart via `.lnk` Freebuff picks up `.env` itself... well, it depends on the launcher. If Freebuff wrapper doesn't read .env, you need a launch-wrapper (`start-buffy.bat` that exports .env to process.env and starts `Freebuff.exe`).
